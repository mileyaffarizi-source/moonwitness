# BLUEPRINT-ASSETS-CHARACTER — CHARACTER CANON & VISUAL SHEETS

**Document ID:** MW-BP-CHR-001 · **Version:** 1.0.0  
**Parent:** [BLUEPRINT-DESIGN-ASSETS.MD](./BLUEPRINT-DESIGN-ASSETS.MD) · **Task registry:** [tasks.json](./tasks.json)

## 1. Purpose

Govern fictional character records and approved character-related visual assets. A character is a canon entity, not simply an image with a name. Identity, aliases, appearance, relationships and chronology must be supported by authored source or explicitly labeled as proposed.

## 2. Character record

Each record includes immutable character ID; exact authored name/spelling; aliases stored separately with source/status; source work/world/edition/chapter/scene; creator when known; fictional/canon state and version history; appearance description supported by source or labeled proposed; traits/role/perspective when known; evidence-backed relationships; timeline references only when sourced; asset references and rights; content warnings/restrictions.

Do not infer a real person's identity or sensitive traits from character metadata.

## 3. Alias policy

Aliases may represent a confirmed pseudonym, title/role, spelling/translation variant, in-story identity, unresolved alias or editorial association. Each alias needs type, source, evidence, status and reviewer. Do not collapse aliases automatically. Similarity matching only suggests a candidate relation; an approved editorial decision canonizes it.

For **0. THE SHADOW**, preserve the recorded aliases **Isa / Ys / R / 163 / Dancer / Runaway / Not Untouched** and phrase **SEBELUM ADA CAHAYA** exactly as metadata/source text. Do not infer a definitive identity.

## 4. Character sheet

An approved sheet may contain front/side/back turnaround, expression range, pose/silhouette, clothing/prop variants, color/material palette, scale/proportion guide, visual motifs, approved context/prohibited interpretations, source references, prompt/brief history, reviewer and canon version.

Do not fabricate unseen canonical details. Separate source-accurate, approved-interpretation and exploratory-concept fields.

## 5. Absolute visual restrictions

Do not create or commission visual depictions of Allah, Prophet Muhammad or Isa/Jesus. This includes portraits, silhouettes, human/animal avatars used as representations, character sheets, in-game units, statues, holograms, symbolic stand-ins, generated scenes or implied visual embodiments.

Textual references may be preserved in original authored context only. If a character request could map to a restricted identity or ambiguous alias, mark it blocked_policy and ask a human to resolve canon in text without requesting or creating a depiction.

## 6. Generation and source workflow

Discover sources → create record with uncertainty → draft source-grounded brief → check identity/restrictions → create exploratory concept only after brief passes → human review → approve/version → export derivatives with provenance.

Do not train models or reuse references beyond documented permitted use.

## 7. Runtime integration

Character profiles distinguish canon fact from editorial note and show source links, version, alias status and relation evidence. Generated designs are never canonical without approval.

## 8. Testing and review

Test alias ambiguity, missing/conflicting sources, revision history, restricted-identity triggers, alt text, responsive crops, asset loading and unauthorized visibility. Character graphs need an accessible list representation.

## 9. Deliverables and ownership

Deliver character/alias schemas, source/evidence policy, character-sheet template, approved visual registry, restriction test cases, provenance, version history and integration UI.

Tasks **CHR-001 through CHR-008** in [tasks.json](./tasks.json).

## 10. Definition of done

No identity is invented from ambiguous metadata; aliases remain evidence-based; approved designs are source-traceable; previous versions are preserved; restricted figures are never depicted.
